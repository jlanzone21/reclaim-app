# Reclaim

Repo: https://github.com/jlanzone21/reclaim-app (private)

A desktop and Android chat app that helps people struggling with
pornography addiction connect to real resources: scripture, local church
small groups, accountability partners, sermons, encouragement, and
counseling centers. It also lets people self-report check-ins ("stayed
strong" / "slipped", with conditions/triggers) and see a local visual
summary of that data — groundwork for a future personal pattern-recognition
(ML) feature.

**Reclaim never replaces human connection.** Every response is designed to
point toward a real person, group, or service — pastor, counselor,
accountability partner, or small group — not to be a substitute for one. A
persistent safety banner, a first-run disclaimer, and always-visible crisis
resources (988 Suicide & Crisis Lifeline, SAMHSA National Helpline) are
built in and should not be removed. Those two numbers are a hardcoded
constant (`CRISIS_LINES` in `web/js/constants.js`), independent of the
resource library and the data-storage changes described below — they work
with zero network and zero database, on purpose.

**On privacy:** chat never leaves the device — Reclaim's AI runs on the
user's own phone or computer (see "The AI agent"), and the only network use
is the one-time model download. Check-in data is a deliberate exception
that's coming: it's moving to Supabase so it can power a real
pattern-recognition feature (see "Data storage"), without tying it to a
name, email, or other real-world identity unless a user chooses to sign in.
Any in-app privacy notice or app-store listing needs to be kept in sync
with this.

## Current state

- UI, Check-In, and Insights are complete (`web/`).
- Chat uses Reclaim's own AI, running entirely on the user's device after a
  one-time ~1 GB download they opt into, personalized from their own
  check-ins. Devices that can't run it (or haven't downloaded it yet) get a
  scripted guide instead ("Basic mode"). Verified on the website in
  desktop Chrome and in the Electron desktop app; **untested on Android** —
  see "Testing the AI on Android" below. See "The AI agent".
- Crisis detection (`CRISIS_PATTERNS`, shared by all agents) is a simple
  keyword/phrase matcher. It is a safety net, not a clinical tool — treat
  any gaps you notice as bugs to fix, and lean toward over-triggering
  rather than under-triggering.
- **Not started:** accounts, and moving the resource library and check-in
  data to Supabase. The design is decided — see "Data storage" below.

## Data storage

Today, everything — the resource library the agent pulls from, and the
user's own check-in history — lives in one local SQLite database, run
entirely client-side via **sql.js** (SQLite compiled to WebAssembly,
`web/js/vendor/`). No native bindings, no server: the exact same code runs
in the Electron renderer, the Android WebView, and a plain browser. The
whole database is persisted as a base64 blob in `localStorage` (see
`web/js/db.js`), which is plenty for this app's scale.

**This is changing.** Both the resource library and check-in data are
moving to a Supabase project (already set up outside this repo) — see
"Planned: cloud data (Supabase)" at the end of this section. The rest of
this section describes the on-device layer as it exists today, which
remains accurate until that migration lands.

- `web/js/db.js` — sql.js init, schema, migrations, and the
  save/load-from-localStorage persistence layer. Schema: a `resources`
  table (type, title, subtitle, body, url, contact, area, duration_min,
  tags, is_sample) covering scripture, sermons, articles, devotionals,
  bible plans, coping mechanisms, small groups, accountability programs,
  and counseling centers (currently ~75 rows across those 9 categories); a
  `bible_plan_days` table for multi-day plans (4 plans, 5–14 days each); a
  `checkins` table for self-reported user data; and an `app_meta`
  key/value table used to track the seed content version.
- `web/js/seedData.js` — the actual bundled content. **All of it is
  placeholder data** — every church, counseling center, and accountability
  program uses a fake (555) phone number, and sermons/articles/devotionals
  use fabricated authors, all flagged `is_sample: 1`. Replace this with real,
  rights-cleared content before anyone relies on this app. Real data you add
  later should use `is_sample: 0` (the UI shows a "Sample" tag on anything
  flagged `is_sample: 1`, so real entries won't be mislabeled).
- `web/js/resourceRepo.js` — the query layer `resourcesAgent.js` calls
  (`getScripture`, `getSermons`, `getBiblePlans`, `getCopingMechanisms`, etc).
- `web/js/checkinStore.js` — same external API as before, now backed by the
  `checkins` table instead of a raw localStorage JSON blob.

### Editing the resource content

`seedData.js` isn't just loaded once — `db.js`'s `ensureSeeded()` re-syncs it
on every app start, gated by `CURRENT_SEED_VERSION`. **Bump
`CURRENT_SEED_VERSION` in `db.js` whenever you change `seedData.js`
materially**, or existing installs won't see the update. On a version bump,
`ensureSeeded()` deletes every `is_sample=1` row and re-inserts fresh from
`seedData.js` — it never touches `checkins` or any `is_sample=0` (real) row
you've added, so this is safe to do repeatedly without losing a user's
check-in history or hand-entered real resources.

**sql.js gotcha, documented so it doesn't get reintroduced**: schema/DDL
setup must use `db.exec(sql)`, not `db.run(sql)` — `run()` silently executes
only the *first* statement of a multi-statement string. This bit us once
already (a `CREATE TABLE` further down `SCHEMA_SQL` was never actually
running).

### Check-in fields and future ML use

Because it's a real SQL database, this is also the natural home for
whatever the future ML/pattern-recognition feature needs — it can just add
tables or query `checkins` directly, no separate data pipeline required.
`checkins` already carries more than the minimum for that: alongside
`type` (resisted/slipped), `tags` (condition/trigger multi-select), and
free-text `notes`, it has three optional 1–5-ish self-rated fields —
`mood_rating`, `urge_intensity`, and `sleep_hours` — chosen because they're
well-documented relapse-risk correlates, not just because they were easy to
add. All three are nullable; the Check-In form never requires them, since a
form that feels like homework stops getting filled in. New columns on an
existing table need their own migration (`migrateColumns()` in `db.js`,
using `PRAGMA table_info` to check before `ALTER TABLE ... ADD COLUMN`) —
`CREATE TABLE IF NOT EXISTS` only helps on a brand-new database.

Everything (chat, check-in, insights) waits on `DB.init()` at startup before
becoming interactive — it's fast (WASM init + an in-memory query), but it is
async, so don't assume the database is ready in code that runs before that
resolves.

### Planned: cloud data (Supabase)

**Status: design decided, not yet implemented.** Two separate things are
moving to a Supabase project set up outside this repo:

1. **The resource library** (scripture, sermons, devotionals, articles,
   bible plans, coping mechanisms, small groups, accountability programs,
   counseling centers, and the website links surfaced to users). Supabase
   becomes the primary source — deliberately no on-device fallback cache
   for the library as a whole, so most of this content requires
   connectivity.

   **Exception — a small "reach this no matter what" set stays on-device,**
   same reasoning as the crisis hotline numbers above: a user in the exact
   moment they need to call their accountability partner shouldn't be
   blocked by a dead connection. This set is fixed at two items for now:
   the user's own accountability-partner contact, and a pastor/mentor
   contact. Both are user-specific data (like check-ins below), not shared
   library content, so they don't belong in the Supabase resource tables
   even once those exist.
2. **Accounts and check-in data**, to power a real pattern-recognition
   (ML) feature and let one person use the same account on desktop and
   Android. Each install starts with **Supabase Anonymous Auth** — a
   private per-install identity with no email or password, so there's no
   sign-up wall on first launch. A user who wants their history on a
   second device can then attach an email or Google sign-in, which
   upgrades that same account and keeps its data. Check-ins are written
   under that identity via a repointed `checkinStore.js`. **Row Level
   Security is required** on every user-data table, so a user can only
   ever read/write their own rows — a hard requirement given how sensitive
   this data is (relapse events, triggers, mood, urge intensity), not an
   optional hardening step.

Why Supabase rather than a self-hosted database (e.g. Postgres on a
developer's computer): logins and a user's history have to work at 2am, so
they can't depend on one machine being awake and online. Supabase also
brings automatic backups (a lost or failed computer would otherwise mean
every user's history is gone) and an audited login system, and its public
key (the "publishable" or older "anon" key) is designed to ship in the app
because Row Level Security enforces access in the database itself. It's plain Postgres, so
`pg_dump` makes leaving possible later. The Supabase `service_role` key
bypasses Row Level Security and must never be in the app or this repo.

### Important: this project cannot live inside a OneDrive-synced folder

The project was originally under `Desktop\Reclaim-chat-agent`, which OneDrive
syncs. OneDrive's Files-On-Demand marks every synced file as an NTFS reparse
point, and Gradle's build-output snapshotting refuses to read those
("Cannot snapshot ...: not a regular file") — this isn't fixable with Gradle
flags, it's a filesystem-level incompatibility. The project now physically
lives at `C:\Users\LANZONEJA25\ReclaimApp\Reclaim-chat-agent`, with a
directory junction at the original OneDrive path so it still opens correctly
from Desktop. **This means the project is no longer backed up by OneDrive**
— use git or another backup method if that matters. If you ever see a
mysterious empty `Reclaim-chat-agent` folder still sitting directly in
OneDrive (not the junction), it's a leftover from this move that can be
deleted once nothing has it open (a reboot clears any stuck lock).

After editing anything under `web/`, sync it into the native project, then

### Windows Gradle troubleshooting: "Unable to establish loopback connection"

If a fresh machine hits this error on `gradlew`, it's a JDK bug where
`java.nio.channels.Pipe`'s self-wakeup socket fails to resolve a valid temp
path for its Unix-domain-socket file. Fix: set
`-Djdk.net.unixdomain.tmpdir=C:\Windows\Temp` for **both** the Gradle
launcher and daemon JVMs — a `JAVA_TOOL_OPTIONS` user environment variable
(covers the launcher) plus `org.gradle.jvmargs` in `android/gradle.properties`
(covers the daemon; already set in this repo). This machine already has the
env var set persistently.

Also note: Gradle 8.14.3 can't compile build scripts on JDK 25 ("Unsupported
class file major version 69") — you need a JDK 21 `JAVA_HOME` for the Gradle
build itself. **Don't rely on Android Studio's bundled JBR for this** — it
tracks newer JDKs and had already moved to JDK 25 as of a September 2026
Android Studio update, breaking this again. This machine has a dedicated
Eclipse Temurin 21 install for exactly this purpose:
`C:\Program Files\Eclipse Adoptium\jdk-21.0.12.101-hotspot`.

## Release build (signed)

```bash

```

Output: `android/app/build/outputs/apk/release/app-release.apk`. Signed with
`android/app/reclaim-release.keystore` — passwords are in
`android/keystore.properties`, which is gitignored (never commit either
file). **Back up the keystore somewhere safe** — if you lose it, any future
release build gets a different signing identity and Android won't treat it
as an update to an already-installed copy. This keystore is self-signed and
not tied to a Play Store listing; it's enough to install and run the app as
a normal release build.

## The AI agent

Reclaim uses **one** AI: a small open model (Qwen3.5 2B) that runs **inside
the app, on the user's own device**, using its graphics chip through
WebGPU. There's no server, no API key, and no third-party AI provider:
conversations never leave the device, and the project controls the model,
the prompts, and which resources can ever be shown.

All agents share one event contract, defined in the header comment of
`web/js/resourcesAgent.js`:

```js
await agent.send(userText, {
  onCrisis: ({ lines }) => {},
  onToolCallStart: ({ id, name, input }) => {},
  onToolCallEnd: ({ id, output }) => {},
  onTextDelta: (chunk) => {},
  onDone: () => {},
});
```

- **`ReclaimAgent`** (`web/js/reclaimAgent.js`) — the agent the app uses.
  For each message:
  1. The crisis check runs first (below).
  2. The model picks **at most one resource type** from a fixed list
     (`AGENT_ROUTER_PROMPT`), as schema-constrained JSON, so it can only
     answer with a valid option, `off_topic`, or `none`. A keyword check
     (`RECLAIM_ON_TOPIC`) overrides `off_topic` for anything about feelings,
     faith, temptation, or relationships — telling a struggling person "I
     can't help with that" is the worst failure this app can have.
  3. The app looks the resource up (`executeAgentTool` → `ResourceRepo`),
     shows it as a card, and writes the sentence introducing it itself (the
     `intro` on each tool in `agentTools.js`).
  4. The model writes 1–3 sentences of warmth (`AGENT_SYSTEM_PROMPT`). It's
     told only the *category* of card shown — never titles, verses, or
     contacts.
  5. The reply is checked before it's shown (`cleanReply`): any sentence
     containing a Bible reference, a quoted passage, a phone number, or a
     link is removed, and it's capped at three sentences.

  Off-topic requests get a fixed reply without the model writing anything.
  The agent keeps the last 6 turns; "clear conversation" starts a fresh
  agent, so the model forgets the old conversation too.

  **Why it's built this way:** WebLLM only offers real tool calling on
  7–8B models, far too big for phones. And in testing, 1.7–2B models given
  resource details misquoted scripture (attributing made-up words to real
  references), invented organizations, and said things like "you can reach
  me at 988." Keeping every specific in app code means the model can't get
  one wrong.
- **`ResourcesAgent`** (`web/js/resourcesAgent.js`) — **Basic mode**:
  scripted keyword matching, no model. `ReclaimAgent` hands a message to it
  whenever the AI isn't ready (not downloaded, still downloading, or the
  device can't run it) or fails before replying, so chat always answers.

**Crisis detection runs before the model is involved** — the same
`CRISIS_PATTERNS` check (`agentIsCrisis` in `agentTools.js`) gates both
agents. It must never depend on model judgment, so it's a hard gate, not an
instruction in a prompt (the prompt also tells the model to mention the 988
Lifeline if someone sounds hopeless, as defense in depth). A crisis message
gets the hotline card and `CRISIS_REPLY` (`constants.js`) with zero model
calls; it stays in the conversation history so later replies have that
context.

**Personalization** (`web/js/personalContext.js`): each reply's prompt
includes a few plain sentences built from the person's own check-ins —
their recent trend, when they last slipped, the situations they mark most,
whether slips cluster late at night, and their latest note — plus the day
and time. It's deliberately qualitative ("a few days ago", "mostly stayed
strong") because small models recite numbers back. Everything stays on the
device. When check-ins move to Supabase, this reads from wherever
`CheckInStore` gets them.

Chat bubbles render plain text; `stripMarkdown` in `app.js` removes any
Markdown the model slips in.

### The model and how it runs

- **`web/js/localModel.js`** checks support (a WebGPU adapter; `shader-f16`
  selects the q4f16 build, otherwise q4f32), downloads and caches the model,
  and generates (Qwen "thinking" off, temperature 0.3, a mild repetition
  penalty).
- **Library:** `web/js/vendor/web-llm.js` is `@mlc-ai/web-llm` (version
  pinned in `package.json`) converted to a plain script by
  `npm run vendor:webllm`, so `web/` still loads only classic `<script>`
  files. It's 6 MB and loads only once someone turns the AI on.
- **Model:** `Qwen3.5-2B-q4f16_1-MLC`, about 1 GB, with a 4k-token context
  (history and prompts are clipped to fit). Weights download from Hugging
  Face and the compiled GPU code from GitHub, then live in browser storage
  (Cache Storage, or IndexedDB where that's unavailable).
- **Nothing downloads without a tap.** The chat view offers it; the badge in
  the header (Basic mode / Downloading 42% / Reclaim AI) opens the same
  panel, including a plain-language reason when a device can't run it. Once
  downloaded, it loads automatically on later visits.
- **Why Qwen3.5 2B:** Qwen3 1.7B was tested first with the same prompts and
  followed instructions noticeably worse (quoted made-up verses, answered
  off-topic requests). Qwen3.5 2B is about the same download (1.03 vs 0.94
  GB) and was clearly better, especially at warm, non-judgmental replies.
- **Measured on an M4 Pro Mac:** download and setup in 30–40 s on a fast
  connection; ready in about 1 s on later visits; 1–2.5 s per reply (the
  first reply after loading takes a few seconds while the GPU warms up); the
  page never froze during download or generation. Verified on the website in
  desktop Chrome and in the Electron desktop app loaded from `file://`,
  including that the downloaded model survives quitting and relaunching.

**Privacy:** conversations and check-in context never leave the device.
The one-time download does contact Hugging Face and GitHub (which see the
device's IP address, not anything the person typed). The first-run notice
(`index.html`, versioned by `WELCOME_VERSION` in `app.js` so existing users
see changes) tells users their conversations stay on the device — keep that
true. Older versions stored users' own Claude/Gemini API keys in
`localStorage`; `app.js` deletes those on startup.

**Known limits:**
- The router sometimes shows a card nobody asked for (a devotional for "I
  can't sleep", coping ideas after "I just slipped"). Not harmful, since the
  app exists to surface resources, but worth tuning with more examples.
- The model needs roughly 2 GB of GPU memory. Low-memory phones may fail to
  load it and fall back to Basic mode with a reason. If that's common,
  `Qwen3.5-0.8B` (about 430 MB) is the next option, likely just for phones.
- Needs WebGPU: current Chrome and Edge on computers, recent Safari, and
  Chrome on Android 12+. **Android's embedded WebView — what the Android app
  runs in — is unconfirmed.**

### Testing the AI on Android

Build a **release** APK and install it over the existing app. It's signed
with the same key, so the phone keeps its check-ins. (A debug build is
signed with a different key; Android won't install it over the release app,
and uninstalling first wipes that phone's data. Only use debug builds on a
phone without real data.)

```bash
npx cap sync android
cd android
.\gradlew.bat assembleRelease
```

Install `android/app/build/outputs/apk/release/app-release.apk`, open Chat,
and tap the badge in the chat header:

- **"This device can't run Reclaim's AI…"** with a reason → the WebView
  doesn't support it. The reason says which part is missing (WebGPU itself,
  or a compatible graphics processor).
- **A download offer** → WebGPU works. Tap Download (on Wi-Fi), wait for
  "Reclaim AI", and send a few messages. If it fails with a memory message,
  the phone can't fit the 2B model.

For more detail, use a **debug** build on a spare phone (release builds
can't be inspected): connect it by USB with USB debugging on, open
`chrome://inspect` in desktop Chrome, pick the Reclaim WebView, and run
`await navigator.gpu?.requestAdapter()` in its console (`null` or
`undefined` means no WebGPU). Also check the phone's **Android System
WebView** version (Settings → Apps). As a comparison, open
`https://reclaim128.org` in Chrome on the same phone: if the AI works there
but not in the app, the WebView is the limitation, and Android needs a
native engine instead.
